# Automated Identity Lifecycle Management Using Okta and SCIM 2.0

A hands-on IAM lab demonstrating how Okta Lifecycle Management can provision users and groups to a custom SCIM 2.0 application.

I built a lightweight SCIM server with **Python and Flask**, exposed it to Okta through an **ngrok HTTPS tunnel**, and used it as the target application for provisioning tests. Building the target application made it possible to inspect the SCIM API requests received during the lifecycle events.

> **Lab/demo project:** This is a learning implementation, not a production-ready SCIM service. It uses a local JSON file for storage and Flask's development server. Do not expose it publicly with real user data or production credentials.

## Project goals

- Connect Okta to a custom SCIM 2.0 endpoint using HTTP Bearer token authentication.
- Create a target-app account when a user is assigned in Okta (**Joiner**).
- Update a target-app account when user profile attributes change (**Mover**).
- Deactivate a target-app account when the user is unassigned (**Leaver**).
- Push Okta groups to the target application.
- Inspect the HTTP requests and responses generated by the provisioning workflow.

## Architecture

```text
┌─────────────────────────────┐
│ Okta Lifecycle Management  │
│ Identity source             │
└──────────────┬──────────────┘
               │ SCIM 2.0 over HTTPS
               │ Authorization: Bearer <token>
               ▼
┌─────────────────────────────┐
│ ngrok HTTPS tunnel          │
│ forwards to localhost:5000  │
└──────────────┬──────────────┘
               │
               ▼
┌─────────────────────────────┐
│ Python / Flask SCIM server  │
│                             │
│ /scim/v2/Users              │
│ /scim/v2/Groups             │
│ /scim/v2/ServiceProviderConfig│
│ /  (web dashboard)          │
└──────────────┬──────────────┘
               │
               ▼
       scim_data.json
       (local runtime data)
```

## Technologies used

| Technology | Purpose |
|---|---|
| Okta Lifecycle Management | Identity source and provisioning orchestration |
| SCIM 2.0 | Standard API for user and group provisioning |
| Python | Server-side implementation |
| Flask | HTTP routes and API responses |
| ngrok | HTTPS tunnel from Okta Cloud to the local lab server |
| Bearer token | Authenticates requests to the SCIM endpoints |
| JSON | Local persistence for lab users and groups |

## SCIM endpoints implemented

| Endpoint | Methods | Purpose |
|---|---|---|
| `/scim/v2/ServiceProviderConfig` | GET | Advertises provider capabilities |
| `/scim/v2/Users` | GET, POST | List and create users |
| `/scim/v2/Users/<id>` | GET, PUT, PATCH, DELETE | Read, update, partially update, and delete a user |
| `/scim/v2/Groups` | GET, POST | List and create groups |
| `/scim/v2/Groups/<id>` | GET, PUT, PATCH, DELETE | Read, update, partially update, and delete a group |
| `/` | GET | Simple dashboard showing users and groups |

The server also includes Bearer token validation for requests under `/scim/v2`, basic user filtering (`eq`), list pagination parameters, SCIM response metadata, and JSON-file persistence.

## How the lifecycle works

### 1. Joiner — create a user

When a user is assigned to the application in Okta, Okta sends a `POST /scim/v2/Users` request. The SCIM server creates a user record and responds with **201 Created**.

### 2. Mover — update a user

When a supported user attribute is changed in Okta, Okta sends an update request to the target application. In this lab, the server supports `PUT` and `PATCH` for user updates. A successful update returns **200 OK**.

### 3. Leaver — deactivate a user

When the user is unassigned from the application, the lifecycle test sends an update that sets `active` to `false`. The user record remains in the local data store but is marked inactive, rather than being permanently deleted.

### 4. Group Push

The Okta **Push Groups** feature creates the group in the target application and synchronizes group information and membership through the SCIM Groups endpoints.

## Setup

### Prerequisites

- Python 3.10 or later
- pip
- An Okta environment that supports the SCIM provisioning features used in this lab
- ngrok account and installed ngrok agent

### 1. Clone the repository

```bash
git clone https://github.com/<your-username>/Automated-Identity-Lifecycle-Management.git
cd Automated-Identity-Lifecycle-Management
```

### 2. Create a virtual environment and install dependencies

**macOS / Linux**

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

**Windows PowerShell**

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

### 3. Set a lab Bearer token

Use a new random token for your own environment. Do not reuse a token from screenshots, notes, or previous runs.

**macOS / Linux**

```bash
export SCIM_TOKEN="replace-with-a-long-random-lab-token"
python3 scim_server.py
```

**Windows PowerShell**

```powershell
$env:SCIM_TOKEN = "replace-with-a-long-random-lab-token"
py scim_server.py
```

The server listens on port `5000` by default. The dashboard is available at `http://127.0.0.1:5000/`.

### 4. Start ngrok

In a second terminal:

```bash
ngrok http 5000
```

Copy the HTTPS forwarding URL displayed by ngrok. Keep it private if the tunnel is still active. Your SCIM base URL will be:

```text
https://<your-ngrok-host>/scim/v2
```

### 5. Configure the Okta app integration

In the Okta Admin Console:

1. Create or open the app integration used for the lab.
2. Enable SCIM provisioning for the app.
3. Open **Provisioning → Integration**.
4. Set the SCIM connector base URL to your ngrok URL plus `/scim/v2`.
5. Set the unique user identifier to `userName`.
6. Choose **HTTP Header** authentication.
7. Set the Authorization value to `Bearer <your-lab-token>` using the same token configured in `SCIM_TOKEN`.
8. Test the connector configuration and enable the required provisioning actions under **Provisioning → To App**.

Exact menu labels and available provisioning options can vary by Okta org and app integration type.

## Troubleshooting notes

| Symptom | Possible cause | What to check |
|---|---|---|
| `401 Unauthorized` | Bearer token mismatch | Confirm the `SCIM_TOKEN` value and the Authorization header match exactly |
| `404 Not Found` | Incorrect SCIM base URL or path | Confirm the URL ends with `/scim/v2` |
| Connector test returns no users | The target app has no records while import testing is enabled | Create a test user in the lab before testing import |
| Address already in use | Another process is using port 5000 | Stop the old process or choose another `PORT` |
| Okta cannot reach localhost | The Okta service is cloud-hosted | Confirm ngrok is running and use its HTTPS forwarding URL |

## Security notes

- Never commit real Bearer tokens, ngrok authtokens, passwords, or `.env` files.
- `scim_data.json` is runtime data and is intentionally excluded from this repository because it may contain personal information.
- Use synthetic test identities only.
- Stop the ngrok tunnel when the lab is not in use.
- This sample is not hardened for production. A production service needs a production WSGI server, stronger persistence, robust SCIM schema and validation handling, secure secret management, monitoring, and additional security controls.

## What I learned

This lab helped me connect IAM concepts with real API behavior: how Okta initiates provisioning, how a target application responds to SCIM requests, how user lifecycle changes are represented, and how to troubleshoot authentication and connectivity issues by inspecting HTTP requests and status codes.
